### 5. Qualify renderer lifecycle and startup

The continuous estate uses native Three.js/WebGL2 (`engine/engine.ts`); the legacy hall uses R3F (`components/library/World.tsx`, demand loop). Do not replace these with WebGPU or delete the legacy dependency without resolving its routes and fallbacks. Keep the DOM book pages and shared print model intact.

With the proposed `/` portfolio this is confined to `/library`, but still costs repeated decode/upload. Compare a static entrance until explicit entry against safely retaining one engine. Preserve the owner's chosen appearance; prefer a bounded lifecycle change over a renderer rewrite.

**Code-supported lifecycle risks requiring a regression:** `engine.ts:213` creates a PMREM render target without retaining an explicit owner; `load()` can return after disposal with newly loaded GLTF/kit resources; `dispose()` disposes many child-owned objects and mesh geometries but lacks a clear ownership path for every shared material/texture, environment target and shadow target. `Artifact3D` texture callbacks can arrive after disposal and `view()` can start another request before an earlier request for that scan completes. Implement explicit ownership, in-flight deduplication and late-result cleanup. Test rapid entry/exit while loading, context loss and at least five enter→read→report→exit cycles. **A growing leak has not been measured in this inspection**; distinguish code-risk fixes from measured memory improvements and avoid double-disposing shared resources.

The frame loop skips drawing while hidden and report pause is implemented. Preserve those behaviors. It still schedules animation callbacks and updates while idle; indoor fire/dust intentionally keeps the view animated. Measure idle/hidden/report CPU and GPU work, and limit optional animation when it contributes no visible result. Keep reduced motion, sound consent, Stop, page-turn correctness and input ownership. Avoid per-frame temporary allocations in the measured hot paths only; do not trade code complexity for an unmeasured win.

Maintain genuine shader/texture warm-up and readiness (`engine/readiness.ts`), which already fixed a first-frame stall. The historical desktop baseline was 5.81 s click→ready and p95 16.8 ms, with 58.6–60 fps depending on action; phone-width figures used the same workstation GPU. Rebaseline the actual candidate before changing startup or paper resolution. Do not hide loading time in the FPS average or call phone emulation physical-phone qualification.
